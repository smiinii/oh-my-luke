# 2026-09-09 격리 재감사

**판정: 실제 AI 실험 격리 미통과, PR #38 병합 보류.** 준비 회귀 테스트의 통과와 실제 실험 준비 완료는 다르다. 합성 테스트 수치를 실제 비교 결과로 사용하지 않는다.

## 이전 검증에서 빠진 것

`e8c86a6`에서 임시 파일과 무해한 후보 코드만으로 다음 세 가지를 재현했다. 사용자 비밀값이나 다른 앱의 데이터는 사용하지 않았다.

| 재현 | 영향 | 보완 |
|---|---|---|
| 후보 테스트가 평가 중 옆 디렉터리의 정답 마커를 읽음 | 작성자뿐 아니라 테스트 실행도 상대 정보를 얻을 수 있음 | 평가 전용 읽기 허용 목록, 별도 scratch |
| 후보 테스트가 Judge 클래스를 재컴파일해 덮어씀 | 고장 난 원본도 성공 판정 | 실제 classpath를 읽기 전용으로 분리 |
| 후보 클래스 초기화가 성공 문구를 출력하고 종료 | 검사 전체를 건너뛰고 성공 판정 | Java는 관측값만 출력, 기대값과 최종 판정은 외부 Python에 유지 |

`test_audit.py`의 처음 세 공격 테스트는 수정 전 모두 실패했다. 수정 후 정상 기준 구현 통과와 공격 거부를 함께 검사한다. 컴파일 자체가 깨져 공격이 실패한 것을 보완 성공으로 판단하지 않는다.

## 추가한 방어와 검사

- 평가 프로세스에는 JDK·클래스·필수 시스템 파일과 독립 scratch만 제공한다. 후보가 만든 JVM의 네트워크는 차단한다. 작성자에게 제공하는 공통 네트워크 정책과는 별도다.
- 각 테스트 프로세스의 scratch를 새로 만들며 다른 평가 공간도 읽을 수 없게 한다.
- macOS 평가 프로세스는 기본 거부, 초기 실행 파일만 허용하며 fork·Mach IPC·네트워크를 허용하지 않는다. Linux는 최소 rootfs와 별도 PID·network namespace를 사용한다.
- 작성자가 호스트 조정 프로세스에 신호를 보내는 경로와 macOS Data 볼륨 대체 경로를 검사한다.
- 후보 트리의 특수 파일·하드링크·과도한 디렉터리·깊이·파일 수·바이트 수를 제한한다. 로그 FIFO·하드링크도 집계하지 않는다.
- Git 환경변수·템플릿이 시작 저장소를 바꾸지 않도록 고정한다.
- 평가 전체 120초, JVM heap 256 MiB·metaspace 128 MiB·활성 CPU 2개로 제한한다. 이 값은 작은 벤치마크 전용이며 사용자 전역 Java 설정은 변경하지 않는다.

## 기존 로컬 경로의 미통과 조건

1. **작성자 → 호스트 HTTP 중계 우회가 재현된다.** 직접 읽을 수 없는 마커를 테스트 전용 HTTP 서버가 대신 읽으면, open-network 작성자는 이를 받을 수 있다. `test_evaluated_code_cannot_use_host_http_relay`는 평가기 차단과 작성자 우회가 남았다는 사실을 함께 검사한다. 이 테스트의 통과는 우회 해결을 의미하지 않는다.
2. 호스트 전체를 읽기 전용으로 제공한 뒤 일부 경로를 숨기는 방식은 모든 위치의 비밀값·스킬·훅·설정·Unix 소켓을 격리한 환경이 아니다.
3. 공개 저장소의 기준 구현 재다운로드, 외부 MCP/서비스를 통한 상대 결과 접근을 아직 통제하지 않는다. 인터넷을 몰래 차단해 이 요구를 충족한 것으로 바꾸지 않는다.
4. macOS 작성자 프로세스 그룹은 detached 자식을 완전히 포함하지 못한다. Linux에서도 전체 프로세스·메모리·디스크 자원 한도는 별도 환경 수준의 검증이 필요하다.
5. 실제 Codex·OMX·OML의 설정·인증·전체 세션 계측은 아직 검증하지 않았다.

`readiness.py`는 위 조건을 명시적으로 BLOCKED로 반환하고 `require_live_ready()`는 실제 실행 승인을 거부한다. 실제 AI 실행 CLI 진입점도 없다. 단순히 테스트 수가 늘었다고 true로 바꾸지 않는다.

## 다음 통과 기준

- 동일 사양의 일회용 실행 환경에서 호스트 개인 파일과 IPC를 분리한다.
- 공통 인터넷·도구는 유지하면서 상대 자료/정답에 대한 직접·중계·원격 접근 경계를 정하고 실제 실패를 검증한다.
- 세 실행기의 실제 적용 설정과 자식 세션을 검증한다. 재개·시간 초과 후에도 이전 실행에 접근하지 못해야 한다.
- 메모리·프로세스·디스크 한도를 환경 수준에서 검증한다.

## 같은 날 추가 보완: 오프라인 일회용 환경

`--container-image` 경로를 추가했다. 위의 기존 open-network 우회 경로를 실제 작업 환경으로 승인하지 않고, 호스트 bind mount·소켓·네트워크가 없는 새 Linux 컨테이너를 실행마다 생성한다. HOME·캐시·tmpfs를 공유하지 않는다. 컨테이너를 동결한 뒤 읽기 전용 보조 컨테이너가 해당 실행의 후보 파일만 회수한다. 작업자 종료만 믿고 살아 있는 자식과 같은 파일을 채점하지 않는다.

- 정상 javac/java 실행, 실제 호스트 HTTP 마커 차단, 이전 HOME 미노출, IPv4/IPv6 외부 연결 실패를 검사한다.
- rootfs 읽기 전용, UID 1000, capability 0, no-new-privileges, CPU/메모리/PID 한도를 검사한다. 프로세스·임시 디스크 초과와 메모리 과다 할당도 실행한다.
- 후보 회수는 크기 제한과 tar 경로·링크·특수 파일 검사를 통과해야 한다. 제한·환경 오류는 성공으로 판정하지 않는다.
- 초기 구현에서 읽기 전용 rootfs로의 파일 전달과 tmpfs 회수 실패를 정상 작업 테스트가 발견했다. stdin 입력과 전용 tmpfs 볼륨/읽기 전용 회수기로 수정했다. 시작 실패를 공격 차단 성공으로 세지 않는다.
- 인터넷은 **허용했다고 주장하지 않는다**. 준비 단계에서만 `network=none`이며, 실제 AI의 외부 자료·인증·MCP 허용 정책은 계속 미통과다.
- 조정자 프로세스의 강제 종료·호스트 장애 후 자동 청소, 컨테이너 엔진/커널 취약점, 모든 원격 정답 유출은 아직 보증하지 않는다. 현재 테스트는 관리자가 정상 작동하는 실행의 정리 범위를 검증한다.

## 배포 재현성의 별도 원인과 수정

Temurin 21.0.12 Linux x64에서 두 압축파일의 해시 불일치를 재현하고 원본을 보존했다. tar 내부 비교에서 `lib/runtime/lib/modules`만 달랐고, `jimage extract`로 `java.lang.invoke`의 Species/Holder 클래스 19개 차이를 확인했다. CDS나 압축 시각 차이가 아니었다.

`--disable-plugin generate-jli-classes`로 링크 시점 사전 생성을 제외한 후 세 번 연속 SHA-256 `ae81d14f9bdddff8d191d7aaaffc1c7606cc99531991f3d664c25e5ab1da1720`이 일치했다. 이 옵션은 [jlink의 플러그인 비활성화 기능](https://docs.oracle.com/en/java/javase/21/docs/specs/man/jlink.html)을 이용한다. 사전 생성 최적화를 제외하므로 초기화 성능 영향은 별도 측정 전이며 속도 향상을 주장하지 않는다.

CI는 `scripts/release/verify-reproducible.py`로 최초 결과를 포함한 3개 압축파일·각 빌드 로그·파일별 차이 JSON을 보존한다. 실패 후 재실행해 초록색만 남기는 방식으로 처리하지 않는다.

최종 로컬 검증: Docker를 활성화한 전체 준비 테스트 53개 중 52개 통과, Linux 호스트 전용 1개 제외. 컨테이너 전용 10개는 모두 실제 실행해 통과했다. A 과제의 3개 가짜 실행 모두 성공했다. Java 회귀 테스트와 macOS/Linux 패키지 수명주기 검사도 통과했으며, 두 OS 각각 3개 압축파일의 해시가 일치했다. 실제 AI opt-in 테스트는 실행하지 않았다. 원격 CI의 OS별 skip과 결과는 PR Checks를 별도로 확인한다.

유한한 함수 검사로 모든 악성 JVM 프로그램의 의미적 정확성을 증명하지는 않는다. 이번 수정은 재현한 우회 경로를 닫는 것이며 OS 취약점이나 모든 부채널에 대한 보증이 아니다. [bubblewrap 공식 보안 설명](https://github.com/containers/bubblewrap/blob/main/SECURITY.md)도 실제 경계가 실행 인자와 상위 정책에 달려 있다고 명시한다.

## 추가 복구 검증

자원 생성 요청 전에 실행 UUID와 소유권을 `local-runs/recovery`에 원자적으로 기록하고 파일·디렉터리를 fsync한다. 각 실행은 잠금을 유지하며, 새 컨테이너 진입 또는 `bench.py recover`에서 잠금이 풀린 미정리 기록을 회수한다. 컨테이너/볼륨의 UUID 라벨까지 일치해야 제거한다. 생성 응답을 받기 전 중단돼도 사전 기록한 이름으로 확인할 수 있다.

실제 조정자 프로세스를 SIGKILL로 종료한 테스트에서 남은 자원을 회수하고 `INTERRUPTED`·`totalTokens=null` 기록을 보존했다. 활성 잠금 건너뛰기, 엔진 접속 실패 시 새 진입 거부, 복구 재실행의 멱등성, 다른 소유자 자원 보존도 검사했다. 기록은 작업자에게 마운트하지 않는다. 이것은 재실행 전에 정리하는 기능이며, 조정자가 없는 동안 즉시 정리하는 상주 서비스나 실제 전원 차단 시험은 아니다.
