# Security

## 권한 모델

OML은 명령어 문자열 허용 목록이 아니라 작업 능력과 정확한 대상을 기준으로 `ALLOW`, `ASK`, `DENY`를 판정한다.

### DENY: 사용자도 해제할 수 없는 불변식

1. AI와 하위 프로세스는 `.oml`의 권한·상태·이벤트를 직접 읽거나 변경할 수 없다.
2. 검증된 운영체제 샌드박스가 없거나 우회가 요청되면 외부 프로세스를 실행하지 않는다.
3. API 키·토큰·인증서의 실제 값은 AI 문맥, 명령 인자, 환경 변수, 상태, 이벤트, 출력에 넣지 않는다.
4. 운영체제 보호 경로, 프로젝트 메타데이터, 프로젝트 루트 또는 승인되지 않은 외부 사용자 데이터를 훼손하지 않는다.

저장된 승인과 프로젝트 자율 실행 모드는 이 불변식보다 항상 우선순위가 낮다.

### ALLOW: 기본 자동 실행

- 프로젝트 파일 읽기·검색·일반 수정
- 체크포인트 가능한 파일 생성·소규모 삭제
- 격리된 프로젝트 사본에서의 빌드·테스트·린트·포맷
- 로컬 상태만 사용하는 프로세스
- 이미 정확한 범위로 승인된 작업

### ASK: 선택형 승인

- 새로운 인터넷 접근과 의존성 설치
- 프로젝트 밖 사용자 경로
- Git push, 발행, 배포 등 외부 변경
- 대량·재귀 삭제
- Docker와 외부 데이터베이스 같은 호스트 기능
- 향후 인증 중계기를 통한 비밀정보 사용

승인 범위는 `이번만`, `현재 실행`, `현재 프로젝트`, `거부`다. 능력, 대상, `toRealPath()`로 고정한 실제 프로젝트 루트, 실행 또는 작업 ID와 만료 시각이 일치할 때만 재사용한다. 프로세스 대상은 호출자가 붙인 이름이 아니라 실제 실행 파일·전체 인자·작업 디렉터리·정렬된 환경·네트워크 범위의 길이 접두어 직렬화 SHA-256으로 만든다. 일회 승인은 프로젝트별 운영체제 파일 잠금 안에서 원자적으로 소비하고 `.oml/permissions.json`에 소비 결과를 저장한다.

사용자가 프로젝트 자율 실행을 켜면 `ASK` 작업을 다시 묻지 않는다. 실행 사실은 사용자에게 알리며 `omluke permissions reset`으로 다시 승인 방식으로 돌아갈 수 있다.

## 구조화 파일 도구

- 셸을 통하지 않고 읽기, 쓰기, 디렉터리 생성, 이동, 삭제를 각각 구조화한다.
- 원시 `..`, 심볼릭 링크, `.oml`, 비밀 파일, `.git` 직접 변경과 프로젝트 루트 삭제를 거부한다.
- 변경 전에 `.oml/runs/<run-id>/file-checkpoints/`에 원자적 복구 체크포인트를 저장한다. 최초 체크포인트는 같은 작업 ID의 재시도에도 덮어쓰지 않으며 요청 지문이 다르면 실행을 거부한다.
- 체크포인트는 프로젝트·실행·권한 대상·복구 root에 결속되고 OML 전용 키의 HMAC으로 무결성을 검증한다. 복구는 모든 경로·포함 관계·중복·크기·권한을 선검증한 뒤에만 시작한다.
- 파일 내용과 함께 POSIX 및 DOS 권한을 보존한다. 체크포인트 크기는 파일을 메모리에 읽기 전에 검사한다.
- 대량 삭제는 승인 후에도 체크포인트 크기 한도를 넘으면 fail-closed 처리한다.
- 도구 결과의 파일 내용은 그래프 상태에 직접 넣지 않고 OML 소유 아티팩트로 저장한다.

## 구조화 프로세스 도구

- 셸과 명령 래퍼를 거부하고 절대 실행 파일과 인자 배열만 받는다.
- 호스트 환경을 상속하지 않고 격리된 `HOME`, `TMPDIR`, 제한된 `PATH`를 제공한다.
- 호출자가 제공한 환경 변수는 이름과 무관하게 모두 거부한다. URL user-info, 인증 query, 알려진 토큰 형태와 인증 명령 인자도 실행 전에 거부하며, 향후 범위 제한 credential broker가 추가되기 전에는 원시 비밀값을 전달할 통로를 열지 않는다.
- `.git`, `.oml`, `.env`, `.npmrc`, `.netrc`, `.pypirc`, Maven 설정, 인증 JSON, 키·인증서와 기존 빌드 산출물을 제외한 임시 프로젝트 사본에서 실행한다. 프로세스가 만든 파일은 실제 프로젝트에 반영되지 않는다.
- macOS는 Seatbelt, Linux/WSL2는 bubblewrap을 사용한다. Windows는 검증된 네이티브 어댑터가 추가되기 전까지 프로세스 실행을 거부한다.
- 네트워크는 기본 차단하며 `NETWORK_ACCESS`, `DEPENDENCY_INSTALL`, `EXTERNAL_WRITE` 승인을 받은 실행에서만 연다. 현재 MVP 승인은 도메인 단위가 아니라 해당 구조화 실행의 전체 네트워크 접근이다.
- macOS 프로필은 전역 경로 메타데이터와 시스템 런타임 내용만 읽고, 사용자 파일 내용은 프로젝트 사본·격리 HOME으로 제한한다. 빌드용 자식 프로세스는 허용하되 OML이 실행 중 발견한 모든 자식을 부모 완료·시간 초과 때 강제 종료한다. Linux는 bubblewrap의 기본 PID 1 reaper가 있는 PID namespace에서 자식을 회수하고 부모 종료 시 namespace를 닫는다. reaper를 끄는 `--as-pid-1`은 사용하지 않는다.
- 표준 출력과 오류를 끝까지 비우면서 저장 크기를 제한하고, 토큰 형태를 제거한 뒤 아티팩트로 저장한다.

## 현재 위협 모델의 한계

- OML은 같은 운영체제 사용자 권한으로 실행되는 별도의 악성 호스트 프로세스까지 격리하지 않는다.
- macOS Seatbelt와 Linux bubblewrap의 실제 지원 여부는 시작 시 검증하며, 적용 실패는 실행 실패로 처리한다.
- 승인된 네트워크 프로세스는 현재 도메인별 방화벽을 사용하지 않는다. 도메인 프록시가 추가되기 전에는 사용자에게 전체 네트워크 권한임을 표시해야 한다.
- Docker 소켓, 외부 경로 마운트, 원시 비밀정보 전달은 권한 범주만 정의되어 있고 현재 프로세스 작업공간에는 노출하지 않는다.
- Linux bubblewrap의 실제 외부·형제 파일 차단, 원본 비변경, 네트워크 기본 차단·정확한 승인, 시간 초과 후 자식 제거는 Ubuntu CI에서 실행한다. bubblewrap 설치만 확인하고 실제 namespace 생성에 실패하는 환경도 테스트 실패로 드러난다.
