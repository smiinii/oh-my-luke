# 12. v0.1.0-rc.1 시험 배포 준비

## 무엇을 만들었나

운영체제별 개발 패키지를 사용자가 시험할 수 있는 Release 후보 형태로 확장했다.

- 제품에서 확인 가능한 `0.1.0-rc.1` 버전과 대상 OS·CPU 표시
- `--help`, `--version` 명령
- Java 21과 예제, 설치·제거 스크립트를 포함한 압축본
- 파일별 SHA-256과 두 운영체제 파일을 묶은 `SHA256SUMS`
- 공개 권한 없이 macOS ARM64·Linux x64 파일을 조립하는 CI 드라이런

GitHub Release나 태그를 실제로 만든 단계는 아니다.

## 어떤 순서로 처리되나

```text
RC 버전 고정
→ 각 운영체제에서 앱 이미지 생성
→ Java·Node가 없는 실행 환경을 흉내 내 실행
→ 임시 사용자 경로에 설치
→ 첫 실행과 AI 없는 승인·재개 확인
→ 같은 버전 재설치
→ 제거 후 프로젝트 상태 보존 확인
→ 두 파일과 검증 근거를 다시 모아 SHA256SUMS 생성
→ 만료되는 Actions artifact로만 보관
```

설치하면 프로그램은 버전별 폴더에 놓이고 `$HOME/.local/bin/omluke`가 현재 버전을 가리킨다. 패키지가 현재 OS·CPU와 다르거나 설치 경로가 심볼릭 링크를 거치면 쓰기 전에 중단하고, 설치·제거가 겹치면 운영체제 잠금으로 하나만 진행한다. 최초 설치 루트는 소유 표시까지 완성한 뒤 한 번에 공개한다. 강제 종료 시 잠금은 자동 해제하며, 재설치의 명령 링크와 제거 스크립트는 기존 파일이 사라지는 중간 상태 없이 교체한다. OML은 상주 서비스가 아니므로 명령을 실행할 때만 켜지고 끝나면 종료한다.

제거 스크립트는 OML 소유 표시가 정확한 설치 경로와 명령 링크만 삭제한다. 각 프로젝트의 `.oml`, 수정된 파일과 Codex 로그인은 그대로 둔다.

## 왜 필요한가

기존 CI artifact는 패키지 생성 가능성만 보여 주고 7일 후 사라졌다. 공개 전에 다음 질문에 자동으로 답할 기반이 필요했다.

- 받은 파일이 CI가 검사한 파일과 같은가
- 사용자의 Java 없이 실행되는가
- 설치와 재설치가 다른 프로그램을 덮어쓰지 않는가
- 제거가 프로젝트 이력이나 Codex 설정을 지우지 않는가
- 두 운영체제 파일을 빠짐없이 한 Release에 올릴 수 있는가

드라이런과 게시 권한을 분리해, PR 검증만으로 외부 Release가 생기지 않게 했다.

## 무엇으로 검증하나

- 일반 테스트는 버전 리소스와 `--help`, `--version`, 손상된 배포 파일 거부를 확인한다.
- 패키지 통합 테스트는 실제 압축본과 그 안의 예제로 설치·재설치·제거·상태 보존을 확인한다.
- macOS와 Ubuntu CI는 같은 파일을 두 번 만들고 SHA-256 재현성을 비교한다.
- 조립 job은 각 파일, sidecar와 JSON evidence를 교차검증한 뒤 통합 `SHA256SUMS`를 만든다.
- 모든 드라이런 job은 `contents: read`만 사용하고 Release 생성 단계가 없다.

실제 AI를 호출하지 않으므로 이 검증 자체는 사용자 Codex 사용량을 소비하지 않는다.

## 아직 남은 것

- 사용자가 Actions artifact를 직접 내려받아 설치·실행·제거하는 실기기 확인
- 명시적 승인 뒤 GitHub prerelease를 게시하는 별도 자동화
- macOS Developer ID 서명·공증
- 서로 다른 RC 사이의 실제 업데이트·롤백 검증
- Windows, Intel Mac과 Linux 배포판별 호환성
- Homebrew·WinGet과 자동 업데이트

체크섬은 손상을 발견하지만 게시자의 신원을 증명하지 않는다. macOS 앱 이미지의 현재 무결성 검사도 정식 서명·공증을 대신하지 않는다. 따라서 이 단계만으로 `v0.1.0` 안정판이 배포됐다고 말하지 않는다.
