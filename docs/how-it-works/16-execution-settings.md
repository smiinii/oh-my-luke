# 16. 실행 설정을 보존하고 프로젝트를 구별하기

## 무엇을 만들었나

OML로 작업을 시작할 때 **어떤 모델 설정을 쓰고, 어느 폴더에 기록할지** 정하는 기반을 만들었다. #41의 1단계이며 공개 RC에 배포된 기능은 아니다. 실제 사용 명령과 경계 규칙은 [실행 설정](../execution-settings.md)에 있다.

## 어떻게 흐르나

```text
작업 폴더 확인
→ 사용자 기본 선택 또는 프로젝트 고정 선택 읽기
→ 작업표·이번 실행 옵션을 우선 적용
→ 확정된 작업표와 모델 선택 저장
→ 기존 그래프 실행
→ 중단 후에는 저장된 작업표로 재개
```

예를 들어 기본 모델이 A인데 이 프로젝트만 B로 정했다면 B를 사용한다. 이번 실행에 C를 지정하면 그 실행만 C다. 나중에 기본값을 바꿔도 이미 저장된 명시 모델 C는 바뀌지 않는다. “Codex 설정 그대로 사용”은 실제 모델 이름을 고정한 것이 아니라 상속 선택을 저장한 것이다.

`setup`을 다시 해도 기존 선택을 지우지 않는다. 프로젝트 고정을 해제해도 실행 기록·승인 정책은 남는다. `status`는 선택과 기록 폴더만 보여주며 조회 때문에 새 실행을 만들지 않는다.

## 왜 필요한가

- 전역 설정과 프로젝트 설정을 혼동해 다른 모델을 사용하는 일을 줄인다.
- 프로젝트 하위 폴더에서 실행·재개해도 동일한 루트를 찾아 기록을 유지한다.
- 이름이 같은 다른 프로젝트나 워크트리의 기록은 합치지 않는다.
- 손상된 설정을 기본값으로 숨기면 사용자가 잘못된 환경을 믿게 되므로 명확히 중단한다.

비 Git 폴더에 아직 식별 경계가 없으면 현재 폴더가 기준이다. 이런 경우 의도한 루트를 `--project`로 지정할 수 있다. 홈이나 바탕화면 전체를 프로젝트로 자동 지정하지 않는다.

## 무엇으로 검증하나

- `ExecutionProfilesTest`: 최초 기본값·재설정 보존·설정 상속/해제·동시 초기화·손상/복사/잘못된 JSON.
- `ProjectLocatorTest`, `ProfileStoreSafetyTest`: 하위 폴더·중첩 저장소·워크트리·동명 폴더·심볼릭/하드 링크·잠금·파일 권한.
- `ProfileDefaultsTest`, `StartCliTest`: 작업표/실행 옵션 우선순위, Start·Run·Workflow에서 가짜 AI까지 모델 전달, 재개 시 현재 설정 재조회 금지.
- `ProfileProcessTest`: 별도 JVM으로 설정·변경·승인·재개·다른 프로젝트 조회·분리 HOME·프로세스 잠금 검증. 실제 AI 실행 파일을 찾지 못하도록 테스트 환경도 분리한다.
- `PackagedApplicationTest`: Java가 PATH에 없는 실제 패키지에서 설정·모델 변경 후 설치·재설치·삭제·재설치를 거쳐 설정 파일 해시와 선택이 유지되는지 확인한다.
- 전체 Java 회귀 테스트와 macOS/Linux 패키지 CI는 기존 실행·설치 경로가 깨지지 않았는지 함께 확인한다. 실제 성공 여부는 해당 PR의 테스트 결과로 확인한다.

## 이번에 완성하지 않은 것

실행기 자동 탐지·실제 계정 모델 목록·호환 하네스 하나를 선택하는 대화형 화면은 2단계, 프로젝트별 질문/사용량 조회와 내보내기는 3단계다. 지금의 `switch`는 Codex + OML 모델 설정만 변경한다. OMX·OMC·OMO 실행, 외부 앱의 상태 감지, 하네스 간 후크 격리, 통합 업데이트 기능은 아직 아니다.

따라서 이번 테스트를 토큰 절감 실험이나 모든 하네스 간 완전한 격리의 증거로 사용하지 않는다.
