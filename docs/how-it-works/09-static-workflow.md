# 9. 정적 Workflow: 조건에 따라 움직이고 승인을 기다리기

OML은 이제 여러 단계를 **미리 정한 경로**로 연결할 수 있다. AI 없는 검사, 기존 파일 수정, 사람 승인을 하나의 실행으로 묶는다. 통합 기획안의 10단계에 해당하며, 저장소에서는 Direct·Loop를 마일스톤 8로 묶었으므로 이번은 9다.

## 어떤 일을 하나

예를 들어 “파일이 이미 조건을 만족하면 그대로 끝내고, 아니면 AI로 수정하되 적용은 내가 확인하겠다”를 다음처럼 실행한다.

1. Java 검사로 파일을 확인한다. 통과하면 AI를 건너뛰고 최종 검사로 간다.
2. 실패하면 기존 Direct/Loop 수정 흐름을 실행해 AI 제안을 저장한다.
3. 적용 승인 지점에서 상태를 저장하고 멈춘다. 파일은 아직 바뀌지 않는다.
4. 사용자가 제안을 확인하고 승인한 뒤 재개하면 적용·검증한다. 거부하면 중단한다.
5. 정해진 최종 검사에 통과해야 성공이다. 한도·권한·충돌은 성공으로 처리하지 않는다.

위는 `edit-with-approval.json` 예제의 흐름이다. 모든 작업에 승인이 생기는 것은 아니며, 작업표에서 지정한 지점에서만 기다린다. AI는 **수정 방법**을 판단하지만 검증 기준·권한·단계 순서를 변경하지 못한다.

## 기존 하네스·루프를 버린 것이 아니다

- 같은 GraphRunner와 상태·정책·도구를 사용한다. Workflow 안에 별도 엔진을 중첩하지 않는다.
- Direct/Loop의 파일 수정 단계를 Workflow 그래프 안에 펼친다. 실행 ID와 전체 예산도 하나다.
- 수정 단계의 재시도는 그 단계 안에서 일어난다. 선행 검사를 무조건 다시 수행하지 않는다.
- 분기 뒤 공통 단계로 이동할 수 있지만, 서로 다른 경로를 동시에 실행하는 병렬 합류는 아니다.
- 간단한 작업은 기존 Direct/Loop를 계속 사용한다.

## 장점과 단점도 설계 근거다

장점은 경로·종료·실패 이유를 추적하기 쉽고, 필요 없는 AI 호출을 건너뛸 수 있다는 것이다. 반대로 예상 밖 흐름에는 새 선언이 필요하고, 과한 검사나 반복은 비용을 늘린다.

그래서 첫 버전은 정적·순차 구조로 검증 가능하게 만들었다. **토큰 절약을 보장하는 완성품이라는 뜻은 아니다.** 구체적인 [장단점과 대응](../workflow-usage.md)을 설계 근거로 남겼으며 효과는 비교 실험으로 확인한다.

## 승인 중 꺼져도 이어갈 수 있나

승인 요청·결정을 파일에 저장한다. 프로그램을 다시 켜도 같은 실행 ID로 확인·승인·재개한다. 승인 요청은 특정 실행과 노드 방문, 저장된 입력에만 유효하므로 이전 승인이 새 제안에 재사용되지 않는다.

`approve`는 동의를 저장할 뿐 바로 파일을 바꾸지 않는다. `resume`을 따로 실행해야 진행한다. 승인 대기 중 원본 파일이 바뀌면 적용을 막고 외부 편집을 보존한다. Workflow 승인은 도구 권한을 풀어주는 승인이 아니다.

현재 상태의 기준은 `inspect`와 `state.json`이다. 최초 `handoff.md`는 목표·재개 안내이며 실시간 상태판은 아니다. 승인 대기에도 전체 시간 한도는 흐른다.

## 무엇으로 확인했나

- 가짜 AI: 선검사 통과 시 호출 0회, 실패 분기 수정, 해당 수정 단계만 재시도, 최종 검사 합류
- 저장·복구: 승인 전 후속 작업 없음, 반복 재개 무동작, 강제 JVM 종료 후 새 JVM에서 같은 실행 재개
- 안전성: 거부·취소·오래된 승인·그래프/상태 변경·권한 우회·한도·파일 충돌 차단
- CLI: 모델 선택, 작업표 복원, 승인 결정/실행 분리, 상태·종료 코드
- 예제 JSON을 자동 테스트로 읽어 실제 코드 경로에서 검증

테스트 위치는 `preset/Workflow*Test`, `runtime/ManagedApprovalTest`, `cli/WorkflowCliTest`, `state/CheckpointCodecTest`다. 실제 AI 없이 검증한 것은 OML의 제어 흐름이며 모델의 응답 품질이 아니다.

## 아직 남아 있는 것

사용자가 작은 선언형 JSON을 준비해야 한다. 자연어만으로 그래프를 생성하거나 실행 중 AI가 단계 구조를 바꾸지는 않는다. Auto·자동 컨텍스트·병렬 실행·비교 실험·공개 배포는 후속이다.

각 수정 단계는 기존 파일 하나·64 KiB 제한이며 여러 파일 전체의 트랜잭션/자동 롤백은 없다. 승인 diff 전용 화면도 아직 없어 저장한 제안 파일을 직접 확인한다. 실사용 절차와 OS 제한은 [Workflow 사용법](../workflow-usage.md)에 있다.
