# 8. Direct와 Loop: 파일을 고치고 검사하는 첫 실행 흐름

지금은 사용자가 지정한 **작은 UTF-8 파일 하나**를 AI가 제안하고 OML이 수정·검증할 수 있다. 같은 그래프 커널 위에서 Direct는 한 번 시도하고, Loop는 검증에 실패한 경우만 제한 안에서 다시 시도한다.

## 실제로 일어나는 일

```text
고정 작업표(JSON): 목표·파일·검증·한도·선택한 모델
  ↓
파일 읽기·내용 스냅샷
  ↓
작성자(AI): {path, content} 제안
  ↓
OML: 경로·형식·권한·파일 변경 여부 검사 → 복구 지점 생성 → 적용
  ↓
검사자(Java/고정 명령): 실제 파일 검증
  ├─ 통과 → 성공
  ├─ 검증 실패 → Direct는 종료 / Loop는 한도 확인 후 파일 읽기로
  └─ 권한·샌드박스·파일 충돌·실행기 문제 → 차단하고 종료
```

하네스는 위 흐름이 함께 쓰는 작업표, 컨텍스트, 도구, 권한, 상태 기록과 검증 장치다. 별도의 하네스 엔진이나 두 번째 AI 검사자를 만들지 않았다. 작성자와 검사자의 **책임을 분리**하되, 참/거짓이 명확한 검사는 Java와 사용자가 정한 테스트가 맡는다.

## Direct의 ‘한 번’은 무엇인가

OML이 AI 실행기를 한 번 호출한다는 뜻이다. Codex 내부 모델 추론이 한 번이라는 뜻은 아니다. 파일을 고친 뒤 검증까지 수행하며, 검증이 실패해도 OML이 자동으로 다시 AI를 부르지 않는다.

Loop에서는 이번 파일 내용과 가장 최근의 짧은 실패 정보만 **OML 입력에** 담는다. 이전 대화 전체는 누적하지 않는다. 단, Codex 자체 설정·프로젝트 읽기 기능까지 없앤 것은 아니다.

## 성공과 중단을 어떻게 구분하나

| 표시 | 의미 |
| --- | --- |
| `SUCCEEDED` | 적용한 파일이 지정한 모든 검증을 통과 |
| `VALIDATION_FAILED` | Direct의 유효성 검사 실패 등, 완료 조건 미충족 |
| `LIMIT_REACHED` | 최대 AI 시도·시간·기록 사용량·동일 실패·무진전 제한 도달 |
| `BLOCKED` | 파일 충돌, 실행기 실패, 검증 불가 등으로 더 진행하지 않음 |
| `CANCELLED` | 저장형 실행 취소 |

그래프의 `COMPLETED`는 **종료 노드에 도착했다**는 내부 상태다. 작업 성공과 다르므로 사용자에게는 별도의 `result`를 표시한다. `run`/`resume`은 검증 성공일 때만 종료 코드 0이다.

AI 시도 한도는 작성자 호출 수다. 기존 `inspect`의 `iterations`는 커널 노드 시도 수이므로 다르다. 같은 실패는 중간 작성·적용 노드가 성공해도 누적된다. 한도가 끝난 실행을 `resume`해서 한도를 초기화할 수 없다.

## 저장하고 다시 시작하는 것

- 고정 작업표, 진행 노드, 호출 수와 실패 요약: `.oml/runs/<id>/state.json`
- 파일 스냅샷과 제안: 같은 실행의 `artifacts/preset-content/<SHA-256>.txt`
- 적용 전 복구 지점: 기존 FileTool 체크포인트. `preset.fileCheckpoint`에 식별자가 남는다.
- 외부 검증 결과: `artifacts/preset-validate-<step>/result.json`
- 처음 만든 인수인계 노트는 목표와 재개 명령을 안내한다. **최신 진행의 기준은 `inspect`와 상태 파일**이다.

별도 프로세스의 `omluke resume <id>`는 저장된 작업표로 그래프를 복원한다. 원래 `task.json`을 수정해도 진행 중 작업표는 바뀌지 않는다. 제안 뒤 중단되면 저장한 제안을 적용하며 AI를 다시 부르지 않는다. 파일을 외부에서 바꿨다면 덮어쓰지 않고 멈춘다.

## 무엇으로 확인했나

- 가짜 AI: Direct 성공/실패, Loop 실패 후 성공, 동일 실패 및 시도 제한, 외부 편집 보존, 제안 후 새 서비스에서 재개
- 경계 테스트: 위험 경로·다른 파일 제안·잘못된 JSON·비밀 패턴·큰 파일·스냅샷 변조 차단
- CLI: 모델/추론 강도 재정의, 저장 작업표 복원, 실패 종료 코드와 사용량 표시
- 외부 명령: macOS/Linux 실제 샌드박스에서 `grep` 종료 코드 검사; 미지원 샌드박스는 차단
- 2026-08-31 로컬 실제 Codex 테스트: 임시 파일에 `OML_PRESET_OK` 제안을 적용하고 Java 검증 통과, 1회 OML 호출 및 토큰 보고 확인

테스트 위치: `src/test/java/io/ohmyluke/preset/`, `cli/PresetCliTest`, `tool/ConditionalFileWriteTest`. 실제 AI 테스트는 명시적으로 켤 때만 실행한다. CI는 비용 없는 테스트와 OS별 경계를 확인한다.

## 아직 범용 완성품은 아니다

- 기존 파일 하나, UTF-8, 64 KiB까지만 다룬다. 다중 파일 변경·생성·삭제나 트랜잭션은 다음 범위다.
- 문자열 조건은 문자열의 존재만 증명한다. 프로그램의 정확성에는 적절한 테스트 명령이 필요하다. 검증 강도는 사용자가 정한 검사에 달려 있다.
- 외부 명령은 고정 인자·오프라인·프로젝트 사본에서 실행된다. macOS는 자식 프로세스가 필요한 전체 빌드가 아직 제한되고 Windows 프로세스 검증은 미지원이다. Linux도 의존성 캐시·네트워크 없이 실행 가능해야 한다.
- AI/명령 실행 도중 사용량·총 경과 시간 한도를 정확히 끊는 것은 아니다. 노드 반환 후 다음 노드를 막으며, 그 결과 **제안 뒤 적용·검증 전에 멈출 수도 있다**. 한 호출만큼 초과 가능하다.
- `maxUsage: 0`은 한도 끄기다. 한도를 켰는데 제공자가 토큰을 보고하지 않으면 무료로 간주하지 않고 차단한다.
- 실패해도 이미 적용한 변경은 자동으로 되돌리지 않는다. 검증 실패 파일과 복구 지점을 남기며, 자동 롤백/복구 CLI는 아직 없다.
- 완료 직후 응답 저장 전 크래시의 exactly-once, 악성 동일 사용자 프로세스, 외부 편집기와의 완전한 원자적 동시 편집은 보장하지 않는다.
- 자동 모드 선택, 정적 Workflow, 비교 실험, 공개 배포는 남아 있다. 토큰 절감 효과는 아직 측정하지 않았다.

개발 중 실행 예시는 [프리셋 사용법](../preset-usage.md)을 따른다.
