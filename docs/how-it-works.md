# OML은 지금 어떻게 작동하는가

이 문서는 코드를 읽지 않아도 OML의 현재 동작을 이해할 수 있도록 설명한다. 마일스톤이 끝날 때마다 이미 검증된 동작, 근거, 남은 한계를 여기에 누적한다.

## 전체 그림

OML은 AI 모델 자체가 아니다. 사용자의 목표를 작은 단계로 실행하고, 결과를 검사하고, 필요한 경우 반복하며, 상태와 권한을 안전하게 관리하는 로컬 실행기다.

```text
사용자 목표
→ 그래프가 다음 작업 선택
→ 노드 실행
→ 결과와 진행 상태 기록
→ 완료·계속·중단 판단
→ 다음 노드 또는 종료
```

하네스, 루프, 그래프를 각각 따로 만들지 않는다. 하나의 그래프 커널 위에 다음 실행 방식을 프리셋으로 올릴 계획이다.

```text
하나의 그래프 커널
├── Direct: 한 번 실행하고 검증
├── Loop: 조건을 만족할 때까지 반복
└── Workflow: 정해진 여러 단계를 순서·분기로 실행
```

현재는 AI 연결 전 단계다. 그래프 실행, 중단·재개, 완료 조건, 권한, 파일·프로세스 도구까지 Java API와 테스트로 구현되어 있다.

## 마일스톤 1: 최소 그래프 커널

### 무엇을 만들었나

노드를 실행하고 결과에 따라 다음 노드를 고르는 가장 작은 실행 엔진을 만들었다.

```text
A 실행
→ 검사 노드
   ├── PASS → 종료
   └── FAIL → A로 돌아가 다시 실행
```

노드는 결과와 변경할 상태만 반환한다. 실제 상태 변경과 다음 경로 선택은 `GraphRunner` 하나가 담당한다. 따라서 노드마다 서로 다른 방식으로 상태를 바꿔 실행 기록이 어긋나는 것을 막는다.

### 왜 필요한가

- Direct, Loop, Workflow가 같은 실행 원리를 사용한다.
- 같은 입력과 상태라면 같은 경로를 선택한다.
- 끝없이 반복될 수 있는 그래프는 실행 전에 제한 조건을 요구한다.
- AI 없이도 실행 규칙을 단위 테스트할 수 있다.

### 검증 근거

- `GraphRunnerTest`: 실행 순서, 상태 변경, 전이 기록 검증
- `GraphValidatorTest`: 잘못된 분기, 도달 불가능한 노드, 제한 없는 순환 거부 검증

## 마일스톤 2: 상태 저장과 재개

### 무엇을 만들었나

실행 중 프로그램이 종료되어도 마지막 안전 상태를 파일에 남기고 다시 이어갈 수 있게 만들었다.

```text
.oml/runs/<run-id>/
├── state.json    현재 상태와 제한 카운터
├── events.jsonl  노드 실행과 정책 판정 이력
└── handoff.md    다음 실행이 읽을 인수인계 노트
```

한 노드는 다음 순서로 처리된다.

```text
안전 상태 저장
→ 노드 시작 기록
→ 노드 실행
→ 결과와 정책 판정 계산
→ 새 안전 상태 저장
→ 완료 이벤트 기록
```

노드 실행 도중 멈추면 완료된 것처럼 처리하지 않는다. 재개할 때 마지막 안전 체크포인트로 돌아가 해당 노드를 다시 실행한다. 그래프 구조나 노드 동작이 저장 당시와 달라졌으면 잘못된 재개를 막기 위해 실행을 거부한다.

### 왜 필요한가

- 긴 작업이 중단되어도 처음부터 다시 시작하지 않는다.
- 다음 실행이나 에이전트가 이전 실패와 진행 상황을 확인할 수 있다.
- 두 OML 프로세스가 같은 실행을 동시에 진행하지 못한다.
- 손상된 상태 파일과 불완전한 마지막 이벤트를 안전하게 복구한다.

### 검증 근거

- `ManagedRunServiceTest`: 실행·중단·재개 흐름 검증
- `CheckpointStoreTest`: 원자적 저장, 백업 복구, 손상 처리 검증
- `EventLogStoreTest`: 불완전한 마지막 로그 복구 검증
- `GraphSignatureTest`: 변경된 그래프의 잘못된 재개 차단 검증

### 현재 한계

`inspect`와 `cancel`은 저장 파일만으로 사용할 수 있다. `resume`은 실행할 Java 노드가 다시 연결되어야 한다. 파일만 읽어 그래프를 복원하는 사용자용 프리셋은 아직 구현되지 않았다.

## 마일스톤 3: 완료 조건과 안전 중단

### 무엇을 만들었나

AI의 주관적인 판단이 아니라 Java가 확인할 수 있는 사실과 숫자로 실행 지속 여부를 결정한다.

```text
노드 결과
→ 완료 조건 확인
→ 반복·시간·호출·사용량 한도 확인
→ 같은 실패와 무진전 확인
→ SUCCESS / CONTINUE / LIMIT_REACHED / BLOCKED / CANCELLED
```

예를 들어 테스트 종료 코드가 0인지, 필요한 파일이 존재하는지, 중대한 오류가 0개인지 같은 조건을 사용할 수 있다. 반복 횟수나 시간 한도에 도달하면 성공으로 꾸미지 않고 `LIMIT_REACHED`로 구분한다.

### 왜 필요한가

- “될 때까지 계속” 같은 무한 루프를 막는다.
- 성공, 한도 도달, 권한 차단, 사용자 취소를 구분한다.
- 같은 실패만 반복하거나 상태가 나아지지 않으면 안전하게 멈춘다.
- 나중에 실험할 때 왜 종료됐는지 비교할 수 있다.

### 검증 근거

- `CompletionEvaluatorTest`, `CompletionPolicyTest`: 객관적 완료 조건 검증
- `LimitPolicyTest`: 반복·시간·호출·사용량 제한 검증
- `ProgressTrackerTest`: 같은 실패와 무진전 감지 검증

## 마일스톤 4: 안전한 파일·프로세스 도구와 권한

### 무엇을 만들었나

그래프 노드가 파일을 바꾸거나 외부 프로그램을 실행하기 전에 OML이 작업의 능력과 정확한 대상을 판정하게 만들었다.

```text
도구 요청
→ DENY 불변식 확인
→ 기본 허용 또는 저장된 승인 확인
→ 필요하면 사용자에게 ASK
→ 구조화된 도구 실행
→ 결과를 아티팩트와 그래프 상태에 기록
```

권한 선택지는 다음 네 가지다.

- 이번만 허용
- 현재 실행 동안 허용
- 이 프로젝트에서 계속 허용
- 거부

프로젝트 자율 실행을 켜면 일반적인 `ASK` 작업은 다시 묻지 않는다. 그래도 다음 작업은 사용자 승인으로도 해제할 수 없는 `DENY`다.

- OML 정책과 `.oml` 직접 변경
- 샌드박스 해제 또는 우회
- 비밀번호·API 키·토큰의 실제 값 노출
- 운영체제 보호 경로, `.git`, 프로젝트 루트 훼손

### 파일 변경 흐름

```text
파일 요청
→ 경로와 권한 확인
→ 변경 전 체크포인트 저장
→ 부모 디렉터리 기준의 안전한 파일 연산
→ 성공 상태 기록
→ 실패하면 체크포인트로 복구 시도
```

파일 작업은 심볼릭 링크나 검사 직후 경로를 바꾸는 공격을 따라가지 않는다. 체크포인트는 최초 상태를 덮어쓰지 않고 HMAC으로 위조 여부를 확인한다. 같은 작업을 다시 요청하면 현재 파일이 이전 성공 결과와 같은지 확인한 뒤 중복 실행을 피한다.

### 프로세스 실행 흐름

```text
프로세스 요청
→ 실행 파일·인자·권한 확인
→ 비밀정보 입력 차단
→ 민감 파일을 제외한 프로젝트 임시 사본 생성
→ 운영체제 샌드박스에서 실행
→ 출력 크기 제한과 비밀정보 마스킹
→ 원본 프로젝트와 분리된 결과 기록
```

macOS는 Seatbelt, Linux는 bubblewrap으로 파일과 네트워크 경계를 강제한다. 샌드박스를 검증할 수 없으면 실행하지 않는다. 프로세스가 만든 변경은 실제 프로젝트에 자동 반영되지 않는다.

### 검증 근거

- `ToolPermissionPolicyTest`: ALLOW·ASK·DENY와 승인 범위 검증
- `ProjectPermissionManagerTest`: 승인 저장과 일회 승인 동시 소비 검증
- `FileToolTest`: 체크포인트, 복구, 멱등성, JVM 간 잠금 검증
- `SecureFileOperationsTest`: 심볼릭 링크 경로 교체, FIFO, 파일 권한 보존 검증
- `ProcessToolTest`: 격리 환경, 시간 초과, 출력 제한, 인증정보 차단 검증
- `MacOsSeatbeltSandboxTest`: 실제 macOS 파일·네트워크 경계 검증
- `LinuxBubblewrapIntegrationTest`: Ubuntu CI의 실제 격리와 자식 프로세스 정리 검증
- PR의 커밋별 독립 리뷰 댓글: 발견된 보안 문제와 해결 과정을 보존

### 현재 한계

- macOS MVP는 잔존 자식 프로세스를 확실히 막기 위해 최초 실행 파일 하나만 허용한다. Gradle처럼 자식 프로세스가 필요한 전체 빌드는 네이티브 감독기가 추가되기 전까지 Linux에서 지원한다.
- Windows 파일·프로세스 도구는 검증된 네이티브 경계가 추가되기 전까지 실행을 거부한다.
- 승인된 네트워크 실행은 아직 도메인별 허용이 아니라 해당 실행 전체의 네트워크를 연다.
- Docker, 비밀정보 중계기, 프로젝트 밖 경로 마운트는 아직 실제 프로세스에 제공하지 않는다.

## 지금 가능한 것과 아직 불가능한 것

현재 가능한 핵심:

- 결정적인 그래프 실행과 순환 제한
- 상태·이벤트·인수인계 저장
- 중단 검사, 취소, 등록된 그래프 재개
- 객관적 완료와 안전 중단 판정
- 기억되는 권한과 프로젝트 자율 실행
- 복구 가능한 구조화 파일 작업
- macOS/Linux의 격리된 구조화 프로세스 실행

아직 남은 주요 작업:

1. 로컬 프로젝트 스캐너
2. 가짜 AI 실행기
3. Codex CLI 실행기
4. Direct와 Loop 프리셋
5. 정적 Workflow
6. Baseline 대 OML 비교 실험
7. Java 설치가 필요 없는 운영체제별 패키징
8. 설치·업데이트·삭제 사용자 문서

## 문서와 증거를 읽는 방법

- 이 문서: 코드 없이 현재 동작 이해
- `product.md`: 제품 범위와 하지 않기로 한 것
- `architecture.md`: 개발자가 보는 상세 구조
- `security.md`: 권한과 보안 경계
- `runtime-auth.md`: 사용자의 AI CLI를 연결하는 방식
- `experiment.md`: 토큰 절감과 성공률을 증명하는 방법
- `adr/`: 중요한 결정을 내린 이유
- 테스트와 CI: 문서에 적힌 동작이 실제로 반복 검증됐다는 증거
- PR 리뷰: 문제를 발견하고 수정한 과정의 증거

문서는 주장과 설계 근거를 남긴다. 실제 동작의 증거는 자동화 테스트, 운영체제별 CI, 재현 가능한 실험 결과가 함께 제공해야 한다.

## 다음 마일스톤부터 갱신하는 규칙

새 마일스톤이 끝날 때마다 이 파일에 다음 다섯 가지만 추가한다.

1. 무엇을 만들었는가
2. 사용자의 요청이 내부에서 어떤 순서로 처리되는가
3. 왜 필요한가
4. 어떤 테스트와 CI가 근거인가
5. 아직 지원하지 않는 것은 무엇인가

구현 클래스 목록이나 세부 코드 설명을 길게 복사하지 않는다. 사용자가 프로젝트의 현재 상태와 작동 원리를 설명할 수 있을 정도로만 유지한다.
