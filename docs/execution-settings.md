# 실행 환경 설정과 프로젝트 경계

이 문서는 #41의 **1단계 개발 기능**이다. 공개 `v0.1.0-rc.1`에는 아직 없다. 이번 단계는 Codex + OML 조합의 모델 기본값·저장·재개를 연결한다. 실행기 탐지와 대화형 전환 화면, 다른 하네스 실행, 질문별 사용량 화면은 후속 단계다.

## 설정하기

개발 빌드의 `omluke`로 실행한다. 아래 명령은 AI를 호출하지 않고 OML 설정만 다룬다. Codex나 다른 하네스의 설정 파일·로그인은 수정하지 않는다.

```bash
omluke setup
omluke status
omluke switch --scope global --model YOUR_MODEL
omluke switch --scope project --model YOUR_MODEL
omluke switch --scope project --inherit-model
omluke switch --scope project --inherit
```

- `setup`: 최초 Codex + OML, 모델은 **실행기 설정 그대로 사용**. 기존 설정이 있으면 내용 그대로 유지한다. 설치 스크립트가 사용자의 설정을 덮어쓰는 방식이 아니다.
- `global`: 사용자 기본 선택. 프로젝트 고정이 있으면 그 폴더의 선택은 그대로다.
- `project`: 이 작업 폴더만 고정. `--inherit-model`은 전역 모델을 따르는 것이 아니라 **Codex 자체 모델 설정을 사용하도록 고정**한다.
- `--scope project --inherit`: 프로젝트 고정만 해제해 사용자 기본 설정을 따른다. 실행 기록과 승인 정책은 삭제하지 않는다.
- `status`: 이 폴더에서 OML로 시작할 때 사용할 선택·설정 출처·기록 폴더를 표시한다. 다른 터미널이나 앱에서 무엇이 실행 중인지 감시하는 명령은 아니다.

명시 모델은 계정 가용성이 아직 확인되지 않은 값으로 표시한다. 목록·요금제를 추측하지 않으며 실제 호출 가능 여부는 Codex CLI가 판정한다. 현재 미지원 하네스 조합은 저장할 수 없다.

## 실행과 재개

모델 우선순위는 **이번 실행의 `--model` → 작업표 모델 → 선택된 OML 설정 → Codex 설정**이다. 선택된 OML 설정은 프로젝트 고정이 있으면 그것을, 없으면 사용자 기본값을 사용한다. 추론 강도는 기존처럼 실행 옵션 → 작업표 → Codex 설정이다.

`start`, `run`, `workflow`는 모델 기본값을 작업표의 빈 필드에만 채운 뒤 저장한다. Workflow는 EDIT 단계별 명시 모델을 보존하며 `--model`은 모든 EDIT에 우선한다. `resume/inspect/approve`는 현재 프로필을 다시 적용하지 않는다. 설정을 바꾸거나 현재 설정이 손상되어도 이미 저장된 실행의 명시 모델을 바꾸지 않는다.

**주의:** “실행기 설정 그대로 사용”이라는 선택은 저장하지만, 그때의 Codex 내부 기본 모델 이름까지 고정하지는 않는다. Codex 쪽 설정을 바꾸면 상속 실행의 실제 모델은 달라질 수 있다. 재현 실험에는 명시 모델·실행기 버전·분리된 설정을 사용한다.

## 기록 폴더 결정

1. `--project <작업폴더>`가 있으면 그 기존 폴더로 고정한다. 폴더를 만들지는 않는다.
2. 없으면 현재 폴더에서 위로 올라가 가장 가까운 `.git` 또는 기존 `.oml/profile.json`, `.oml/runs` 경계를 찾는다.
3. Git·OML 경계가 없는 일반 폴더는 기존 동작처럼 현재 폴더를 기준으로 한다. 첫 실행 이후 `.oml/runs`가 경계가 된다. 초기 비 Git 프로젝트의 루트가 애매하면 `--project`를 명시한다.
4. 홈·바탕화면·다운로드·문서 모음 폴더 자체와 파일시스템 루트는 자동 작업 폴더로 쓰지 않는다. 그 안의 별도 작업 폴더를 지정한다.

```bash
omluke --project /absolute/path/to/project status
omluke --project /absolute/path/to/project start job.json --mode auto
omluke --project /absolute/path/to/project resume RUN_ID
```

`--project`는 작업표 경로까지 지정 폴더 기준으로 해석한다. 자동 탐지에서는 명령에 적은 작업표 경로는 터미널의 현재 폴더 기준, 작업표 **안의 대상 파일 경로는 탐지된 루트 기준**이다. 시작 전에 `projectRoot=`를 출력하므로 의도한 폴더인지 확인한다. 과거 하위 폴더에서 독립 실행하던 작업은 `--project`로 그 폴더를 명시할 수 있다.

동일한 폴더 이름을 프로젝트 ID로 사용하지 않는다. 실제 절대 경로를 사용해 다른 저장소·워크트리 기록을 합치지 않고, 같은 실제 폴더를 가리키는 경로 별칭은 동일하게 처리한다. 작업 폴더를 옮기거나 다른 폴더의 프로필을 복사하면 루트 불일치로 중단한다. 자동 기록 이전·통합 기능은 없다.

## 저장과 보호

- 사용자 설정: `$HOME/.oml/settings.json`. `HOME`이 없으면 JVM의 사용자 홈을 사용한다. 실험에서 분리한 HOME을 존중하며 실제 홈 설정으로 재시도하지 않는다.
- 프로젝트 설정: `<프로젝트>/.oml/profile.json`. 기록은 같은 프로젝트의 `.oml/runs/`에 유지한다. `.oml/`은 Git에서 제외되어 있다.
- 조회는 폴더를 만들지 않는다. 저장은 프로세스 잠금 → 기존 형식 검증 → 임시 파일 쓰기·동기화 → 원자적 교체 순서다. 잠금 경합은 기다리며 멈추지 않고 다시 시도하라고 알린다.
- 중복 키·잘못된 타입·지원하지 않는 버전/필드·16 KiB 초과·잘못된 프로젝트 바인딩을 거부한다. 손상된 설정을 조용히 기본값으로 바꾸거나 덮어쓰지 않는다.
- 설정 디렉터리·파일·잠금의 심볼릭 링크, 설정/잠금 파일의 하드 링크(Unix), 일반 파일이 아닌 설정을 거부한다. 새 설정은 POSIX에서 소유자 읽기·쓰기 전용이다. 다른 파일시스템에서는 상속 ACL을 사용하며 원자적 교체 미지원 시 저장을 거부한다.

이 기능은 **설정 선택과 기록 위치 분리**다. 임의의 외부 CLI가 다른 하네스의 전역 스킬·MCP·후크를 읽지 못하게 하는 샌드박스는 아니다. 같은 OS 사용자 권한을 가진 악성 프로세스의 동시 디렉터리 교체나 디스크 손상·전원 장애까지 완전 방어한다고 주장하지 않는다. 비교 실험은 별도 격리 환경과 실행 기록 검증이 계속 필요하다.
